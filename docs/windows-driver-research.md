# ScanSnap SV600: восстановленная Windows-цепочка

Дата фиксации: 29 августа 2026 года. Исследовалась ScanSnap Home 4.0.0 и
подключённый SV600 с серийным номером `AT5HC04450`.

## Вывод

Готовое изображение SV600 создаётся не одной командой сканера. Прошивка отдаёт
RGB-кадр 300 dpi высотой 4429 строк для A3/Auto или 2858 строк для штатного
класса A4/A5, после чего Windows minidriver и ScanSnap Home выполняют несколько
обязательных геометрических и цветовых этапов. Именно
пропуск этих этапов давал на раннем Linux-прототипе радугу, кривые строки,
чёрные края и потерю ближнего угла.

Текущий backend больше не ищет для фиксированных форматов границы собственными
эвристиками. Он воспроизводит доказанные операции производителя:

```text
SV600 USB, RGB8 5572×4429 (A3/Auto) или 5572×2858 (A4/A5) @ 300 dpi
  -> расширение строки minidriver до логической ширины 5832
  -> оптическая карта SV600u-x64.dll
  -> application boundary 5816×4352 (A3) или 5816×2781 (A4/A5/Auto)
  -> P2IDIGCROP.dll
  -> bookbound.dll, flat-content correction
  -> gamma 1.0→1.8
  -> P2IATRES.DLL для 150/200/600 dpi
  -> SV600 17×17×17 sRGB LUT
  -> SsSvcDoUSM2
  -> SsSvcConvRGBToGrayN, если выбран Gray
  -> SANE frontend
```

Wine здесь является только совместимым загрузчиком нескольких 32-битных
image-processing DLL. Windows, виртуальная машина и Windows-драйвер на Astra не
запускаются.

## USB и управление устройством

SV600 виден как два независимых USB-устройства:

| USB ID | Windows name | Назначение |
|---|---|---|
| `04c5:128e` | ScanSnap SV600 | CCD/LED, команды сканирования и полный RGB |
| `04c5:13ba` | USB Camera | UVC 640×480 для движения/page-turn |

Высококачественное изображение приходит только через `04c5:128e`. Камера не
участвует в обычном ручном скане.

Оригинальная программа использует STI user-mode minidriver
`SV600u-x64.dll`, а не TWAIN/ISIS. Для запуска SV600 обязательны
восстановленные prepare-scan команды, включение лампы, модельный `SET WINDOW`
и пауза стабилизации перед `SCAN`. Универсальная последовательность backend
`fujitsu` без этих отличий зависала.

## Форматный ход сканера

Выбор бумаги в ScanSnap Home влияет не только на последующий crop. Сохранённая
Frida-трасса `SV600u-x64.dll` содержит входной `SET WINDOW` 5832×2858 для
малого класса, а заводская A3-трасса — 5832×4429. Статический код
`CSshCtlObj::SetMdmSize` для модели `0x45` подтверждает две высоты:

- A4 и A5 используют один сокращённый аппаратный класс;
- A3 использует полный ход;
- Auto оставлен на полном ходе, чтобы не ограничивать найденный документ.

До остальных команд `CSshCtlObj::SetPreReadMode` передаёт custom capability
`0x8100`. Минидрайвер превращает её в firmware diagnostic `0x117`, то есть
32-байтовый `SET PRE READMODE`. Восстановлены точные поля пакета: X/Y 300 dpi,
composition `5`, escan `0` и размеры в единицах 1/1200 дюйма:

| Формат | Размер, мм | width | length | Аппаратные строки |
|---|---:|---:|---:|---:|
| A5 | 148×210 | 6992 | 9921 | 2858 |
| A4 | 210×297 | 9921 | 14031 | 2858 |
| A3 | 297×420 | 14031 | 19842 | 4429 |

Проверка на подключённом сканере дала A5 8,2 с, A4 8,4 с и A3 11,3 с для
полного вызова `scanimage` вместе с заводской постобработкой. Прошивка вернула
ровно 2858/2858/4429 строк соответственно. Поэтому отдельного третьего хода
для A5 в исследованной версии производителя нет: A5 отличается от A4
pre-read-размером и выходной геометрией, но относится к тому же малому ходу.

## Сырой кадр и оптическая карта

Устройство принимает в финальном `SET WINDOW` ширину `0x5710` единиц, то есть
5572 пикселя при 300 dpi, и возвращает 4429 строк для A3/Auto либо 2858 для
A4/A5. Перед оптической
коррекцией Windows-minidriver разворачивает каждую физическую строку в
логическую строку шириной 5832:

- физические пиксели `0..5571` попадают в `130..5701`;
- в `123..129` семь раз повторяется первый физический пиксель;
- в `5702..5708` семь раз повторяется последний физический пиксель;
- диапазоны `0..122` и `5709..5831` заполняются нулями.

Эта схема проверена на всех 23 перехваченных входных блоках коррекции — 5529
строках с перекрытиями — без единого отличия. Уже логический кадр шириной 5832
содержит стол, а проекция и положения каналов R/G/B зависят от глубины. Одна
homography не может устранить это поканальное нелинейное расхождение.

Исследованный `SV600u-x64.dll`:

- SHA-256
  `abee6d6cd8eb43f2512bad1b9fda9164afab5fc886992c6f9b6ee01134568f4c`;
- таблица по RVA `0x128270`;
- 4700 строк × 6 значений `float32`.

Первые два столбца задают вертикальную поправку R/B (зелёная равна нулю),
следующие три — горизонтальный шаг R/G/B. Вертикаль переводится в Q12
усечением `float*4096`, горизонталь — в Q19 усечением `float*524288`.
Горизонтальный аккумулятор оригинала беззнаковый 32-битный. Знаковый вариант
переполнялся в дальней четверти строки, переносил тёмные данные с другой
стороны и закрывал карандашную `Z` в ближнем левом углу.

Развёрнутая Q12/Q19-таблица имеет SHA-256
`e54baa1b99c89de56b33ac78a5af7d2ce92fcd6717c75dd20c99aaf048c4e0b7`.
В репозитории она хранится как начальная строка и точные `int8`-дельты.

Точная область, передаваемая ScanSnap Home после minidriver:

- начало полного поля: `x=8, y=52`;
- A3: 5816×4352;
- A4/A5/Auto: 5816×2781.

Прототип совпал с перехваченным minidriver output побайтно во всей используемой
области.

## Геометрия A3L/A4L/A5L

Frida-трассы реальных A3, A4 и A5 профилей показали следующие входные точки
`P2IDIGCROP`:

| Формат | NW | NE | SW | SE | Выход 300 dpi |
|---|---:|---:|---:|---:|---:|
| A3L | (430,76) | (5390,76) | (430,3583) | (5390,3583) | 4961×3506 |
| A4L | (1155,76) | (4662,76) | (1155,2556) | (4662,2556) | 3508×2479 |
| A5L | (1668,76) | (4148,76) | (1668,1824) | (4148,1824) | 2481×1747 |

Это фиксированные центральные области производителя. Поэтому правильная
физическая укладка — landscape и по центральной метке. A4/A5 не должны
прижиматься к боковому краю поля. Если выбран A4 для сшитого дела, в результат
попадает именно центральная область A4; видимая рядом часть второй страницы
остаётся снаружи, пока не заходит в эту область.

`P2iDigGetPrm` и `P2iDigCrop` формируют номинальный прямоугольник, затем
`AutoBBLINEModelExtraction` и `ContentModelCorrection` из
`bookbound.dll` повторяют flat-content correction ScanSnap Home. Один
унифицированный helper под Wine дал побайтное совпадение с сохранёнными
заводскими промежуточными TIFF для A3, A4 и A5.

В Auto вызывается настоящий `P2iDigGetPos`; собственный детектор backend
удалён. Для Auto оригинальный матовый Background Pad всё ещё желателен.

A3 не превращается в найденный отдельный A4. Контроль с одним A4 при выбранном
A3 и контроль с двумя A4 рядом дали полный landscape 4961×3506. Это и есть
поведение fixed A3L.

## Цвет и резкость

Выходная ветка ScanSnap Home выполняет:

1. byte gamma `255 * (x/255)^(1/1.8)`;
2. преобразование выходного разрешения;
3. целочисленную трилинейную интерполяцию в SV600 sRGB grid 17³;
4. `SsSvcDoUSM2` с выбранным для SV600 strength 50, radius 2 и threshold 8.

Таблица sRGB перенесена без аппроксимации в
`data/sv600-srgb-lut.inc`. Сравнение каждого промежуточного TIFF позволило
отделить эти операции и восстановить целочисленное округление.

В диагностике также существует ранняя ветка `MakeSRGBAnoBuf` с sRGB и USM для
OCR. Она не является изображением, сохраняемым пользователю: заводской
`BeforeResize` побайтно равен кадру сразу после gamma. После resize применение
нашей 17³ интерполяции дало SHA-256 заводского `AfterSsSRGB`, а применение USM
к этому кадру — SHA-256 заводского `AfterColorModeProcess`, в обоих случаях с
нулём отличающихся пикселей.

Контрольные SHA-256 массивов RGB для A5/150: geometry
`83f307984592ffb42444503cf4ee4542f3f50baee9991738b92fd33a8c630759`, gamma
`ba0d8019f30d3ba7047d3485367755907044d4761d7587a33c4bb990f81f2833`, resize
`86baf80c3fa8904af9bad344251c41a797c86f912def1a8c3c0f81a60c0e641b`, sRGB
`117a28b435759b2edda9dc91792feca133f11ff116078ac2d85441d055710267`, final USM
`438b6a0103005dcf5058d1a7066989fd2f446ad008c368f71fecba759f8b0f27`.

## Разрешение

Оптическое получение всегда остаётся 300 dpi. Перехват A5 Color 150 показал:

| Этап | Размер |
|---|---:|
| после geometry и gamma, до resize | 2481×1747 |
| после resize | 1240×873 |

`PfuSsImgCtl.dll` импортирует `SsSvcGetResizePrm` и `SsSvcResize`;
`PfuSsSvc.dll` передаёт их в `P2IATRES.DLL` как `P2iGetResizePrm` и
`P2iResize`. Прямой вызов этих экспортов под Wine дал ноль отличающихся
пикселей от заводского `AfterResize`; SHA-256 массива RGB в обоих случаях:
`86baf80c3fa8904af9bad344251c41a797c86f912def1a8c3c0f81a60c0e641b`.

Тот же модуль используется для 200 и 600 dpi, включая его правила округления.
600 dpi является интерполяцией из 300 dpi.

## Gray

Перечисление `Pfu.ScanSnap.Home.Data.API.ColorMode` из оригинальной сборки:

```text
COLORMODE_AUTO = 0
COLORMODE_FULL = 1
COLORMODE_GRAY = 2
COLORMODE_MONO = 3
```

В профиле A5 Gray 150 трасса показала два вызова `SsSvcConvRGBToGrayN`:
ранний служебный кадр для анализа и финальный вызов после output sRGB и USM.
Оба вызова используют:

```c
gray = (77 * red + 150 * green + 29 * blue) >> 8;
```

Полный финальный кадр 1240×873, вычисленный как `sRGB -> USM -> Gray`, совпал
с заводским `AfterGrayModeProcess` во всех 1 082 520 пикселях; SHA-256 массива
Gray в обоих случаях:
`636e6129fbec7fad5c8872c3495316749f0306c0ae8a3f98f0ce450f2e71a3cf`.
Контроль без USM отличался в 82 747 пикселях (максимальная разница 66), что
однозначно подтверждает порядок операций. Поэтому Gray 150 получает ту же
геометрию, gamma, resize, sRGB и резкость, что Color 150, а frontend получает
настоящий `SANE_FRAME_GRAY` с одним байтом на пиксель.

## Живая проверка на Astra Linux

Финальный backend был установлен на Astra Linux и проверен непосредственно с
подключённым по USB/IP SV600 через обычный SANE `scanimage`. Эти вызовы
использовали тот же backend, который видят Simple Scan и NAPS2:

| Формат | Режим | DPI | Фактический PNM |
|---|---|---:|---:|
| A3L | Color | 300 | RGB 4961×3506 |
| A4L | Gray | 150 | Gray8 1754×1239 |
| A5L | Gray | 150 | Gray8 1240×873 |
| A5L | Color | 200 | RGB 1654×1164 |
| A5L | Gray | 600 | Gray8 4962×3494 |
| A5L | Lineart | 150 | packed 1-bit 1240×873 |

Все файлы завершились валидными PNM без посторонних байтов перед заголовком.
A3L на сцене из двух A4 имеет те же 4961×3506, landscape-ориентацию и границы,
что сохранённый заводской A3L ScanSnap Home.

## Что сознательно не входит

Не реализованы page-turn, удаление пальцев, ручные контрольные точки и
исправление кривизны раскрытой книги. Для них нужны камера и отдельный
интерактивный workflow; пользователь прямо исключил этот объём из текущей
версии. Обычные плоские A3/A4/A5 и один лист сшитого дела используют
восстановленный заводской cutsheet path.
